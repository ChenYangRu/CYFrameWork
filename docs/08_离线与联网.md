# 08 · 离线与联网（双模架构）

> 这套框架把"单机"和"联机"当成**两条独立的产品形态**，而不是一堆 `if`。
> 一个开关（`gameMode`）决定：要不要起网络、数据以谁为准、玩家从哪个界面进入。
> 目标平台：**微信小游戏 / WebGL 优先**，同时兼容 Android / iOS / PC。

---

## 一、一张图说清两种模式

```
                    ┌──────────────────────────────┐
                    │  Bootstrap.resourcePlayMode   │  资源从哪来（四选一）
                    │  Bootstrap.gameMode           │  玩法走哪条线（二选一）
                    └───────────────┬──────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
       ┌─────────────┐                             ┌─────────────┐
       │  Offline    │                             │   Online    │
       │  离线单机    │                             │   联网      │
       └──────┬──────┘                             └──────┬──────┘
              │                                           │
   不创建 NetworkService                        创建 NetworkService
   数据 = 本地 txt（权威）                      数据 = 服务端（权威）+ 本地缓存
   启动 → 直接进主界面                          启动 → 登录页 → WebSocket 握手
   存档：persistentDataPath/save/<槽位>/        断线：指数退避重连 + 本地缓存续玩
```

**关键点：离线模式下 `NetworkService` 根本不创建。**
业务里 `GameEntry.Network == null` 就是"当前是单机"的天然判据，不需要再传一堆 bool。
（代价：写联网逻辑时必须判空——这是**故意**的，漏判会立刻 NRE 而不是静默走错分支。）

## 二、模式怎么定（优先级三层）

| 层级 | 位置 | 作用范围 | 说明 |
|---|---|---|---|
| ① 最高 | `Bootstrap.gameMode`（Inspector） | **随场景进包，真机生效** | 出包决策：这个包是单机还是联机 |
| ② | 菜单 `框架/游戏模式/*`（EditorPrefs） | 仅编辑器 | 开发期临时切换 |
| ③ | `Assets/Resources/Config/launch.json` 的 `gameMode` | 全局默认 | `0` = 离线，`1` = 联网 |

```json
// launch.json
{ "gameMode": 0 }
```

> 和资源模式（`resource.json` 的 `playMode`）保持同一套"三层覆盖"规则，
> 避免出现"两个设置各说各话"。改完在 Console 第一行就能看到实际生效值：
> `[Launch] 游戏模式=Offline（离线）（存档槽位=default）`

## 三、离线存档：txt + CRUD

### 3.1 文件长什么样

```
<persistentDataPath>/save/<槽位>/
├─ player.txt     主角（单条记录）
├─ items.txt      背包（多条记录）
├─ settings.txt   键值设置（音量/画质/语言…）
├─ slot.txt       槽位元信息（创建时间/最后存档/游玩次数/格式版本）
└─ *.txt.bak      上一次存档的备份（主档损坏时的兜底）
```

`items.txt` 内容示例（**一行一条记录**）：

```
#table=items v1
#saved=2026-11-04T06:12:33Z
#count=2
{"id":"items_638...","name":"道具_1","count":3,"quality":2}
{"id":"items_638..._1","name":"道具_2","count":1,"quality":1}
```

**为什么是"一行一个 JSON"而不是一个大 JSON 数组**

| 方案 | 问题 |
|---|---|
| `JsonUtility.ToJson(List<T>)` | 根上不支持 List，必须包一层壳；泛型壳在不同 Unity 版本上行为不一致 |
| 一个大 JSON 对象 | 一条记录写坏 → 整个存档读不出来；也不能增量对比 |
| **一行一条（本方案）** | 单条损坏只丢一条；`git diff` 逐行可读；真机上拷回来直接看得懂 |

### 3.2 实体定义（3 行就能接）

```csharp
using System;
using GameFramework.Data;

[Serializable]
[DataTable("items")]                    // 表名 = 文件名 items.txt
public class ItemSave : IDataRecord
{
    public string id;                   // ★ 必须是 public 字段：JsonUtility 只序列化字段
    public string name;
    public int count;
    public int quality;

    public string Id { get { return id; } set { id = value; } }   // 接口要求
}
```

> 别忘了 `[Serializable]` 和"字段"这两个前提。
> 写成属性 `public string id { get; set; }` 会**静默不落盘**（JsonUtility 不序列化属性），
> 表现是"明明改了，重进游戏又变回去"。

### 3.3 CRUD API（增删查改）

```csharp
var data  = GameEntry.Data;                 // = ServiceLocator.Get<DataService>()
var items = data.Database.Table<ItemSave>(); // 首次访问自动读盘

// —— 增 ——
var it = new ItemSave { name = "药水", count = 2, quality = 1 };
bool ok = items.Insert(it);                  // id 为空会自动生成；id 冲突返回 false
items.InsertRange(list);                     // 批量，返回成功条数

// —— 查 ——
ItemSave one  = items.Get("items_xxx");      // 按主键（O(1)）
List<ItemSave> rares = items.Find(x => x.quality >= 2);
ItemSave first3 = items.FirstOrDefault(x => x.count > 10);
bool has = items.Contains("items_xxx");

// —— 改 ——
ItemSave p = items.Get("items_xxx");
p.count += 1;                                // Get 返回**引用**，就地改
items.MarkDirty();                           // ★ 改完必须打脏，否则不落盘

items.Update(another);                       // 按主键整体替换（不存在返回 false）
items.Upsert(another);                       // 有则替换、无则新增

// —— 删 ——
items.Delete("items_xxx");                   // 按主键
int n = items.DeleteWhere(x => x.count <= 0);// 条件批量
items.Clear();                               // 清空（内存，落盘要 Save）
```

### 3.4 存档生命周期

```csharp
data.Save();          // 脏表 + 设置 + 元信息 → 磁盘（返回是否全部成功）
data.Load();          // 重新读盘（丢弃内存改动）
data.ResetSlot();     // 清档：删掉本槽位全部文件并重建
data.Flush();         // = Save()，语义化别名，用于结算/付费/切场景
```

自动存档由 `DataService` 挂在主循环上：默认 **20 秒**一次，只在有脏表时才写盘。
调法：

```csharp
GameEntry.Data.AutoSaveSeconds = 10f;   // 0 = 关闭（不建议）
```

退出时 `GameLauncher.Teardown` 会先 `Data.Dispose()`（内部 `Save()`）再拆服务——
**顺序反了会丢掉最后一段进度**，这条写在代码注释里，改的人别调换。

### 3.5 健壮性设计（都是真机上踩过的）

| 机制 | 解决的问题 |
|---|---|
| **临时文件 + 原子替换**（`.tmp` → `File.Replace`，失败退回删+移） | 被系统杀进程时不会留下半截文件 |
| 每次存档留 `.txt.bak` | 主档写坏还能手动救一次 |
| 逐行解析 + 单条容错 | 一条坏数据只丢那一条，不会整个存档报废 |
| 表名/槽位名白名单过滤（只留 `a-z0-9_-`） | 小游戏与安卓沙盒上中文/特殊文件名容易出问题 |
| `FormatVersion` 写进 `slot.txt` | 以后改结构时能判断旧档要不要迁移 |
| 存档目录不可写时**降级为纯内存** | 权限异常也不至于让游戏起不来 |

## 四、联网：WebSocket

### 4.1 为什么必须是 WebSocket

| 平台 | TCP 裸 socket | WebSocket |
|---|---|---|
| Editor / Android / iOS / PC | ✅ | ✅ |
| WebGL | ❌ 没有 BSD socket | ✅ |
| 微信小游戏 | ❌ | ✅（`wss://` + 后台配 socket 合法域名） |

所以 `network.json` 默认 `"transport": 1`（WebSocket）。
**如果配成 0（TCP）但在 WebGL 上跑**，`NetworkService.CreateChannel` 会自动切到 WebSocket 并打一条警告——
避免出现"编辑器好好的、真机连不上"的排查黑洞。

### 4.2 配置

```json
// Assets/Resources/Config/network.json
{
  "host": "127.0.0.1",
  "port": 9000,
  "transport": 1,              // 0=TCP 1=WebSocket
  "webSocketSecure": false,     // 正式环境/小游戏必须 true（wss）
  "webSocketPath": "/",         // 网关挂在 /ws 就填 /ws
  "webSocketUrl": "",           // 非空则直连（如 wss://gw.example.com/ws），忽略 host/port
  "connectTimeout": 8,
  "heartbeatInterval": 10,
  "heartbeatTimeout": 30,
  "autoReconnect": true
}
```

**三条硬规则**

1. **https 页面 / 小游戏必须 `wss://`**，`ws://` 会被当混合内容直接拦掉（浏览器控制台能看到）。
2. 微信小游戏要在**微信公众平台 → 开发设置 → socket 合法域名**里加你的 `wss` 域名，否则连不上。
3. 端口不要写 80/443 之外的奇怪值；走 CDN/反代时用 `webSocketUrl` 直接给整条地址。

### 4.3 协议：完全不变

WebSocket 只是管道，**业务协议与 TCP 一模一样**：

```
[0..3]  bodyLen (uint32)
[4..7]  cmd     (uint32)
[8..11] seq     (uint32)
[12..]  包体
```

一条 WS 消息里可能粘了多个业务包，一个业务包也可能跨消息——
所以 `WebSocketChannel` 内部照样跑 `PacketSplitter` 做流式拆帧。
**业务代码零改动**：`Send` / `Request` / `RegisterHandler` 用法完全一致。

```csharp
net.RegisterHandler(Cmd.LoginAck, p => { ... });
net.Request(Cmd.LoginReq, body, (ok, ack) => { ... });
```

### 4.4 双后端（这是小游戏能跑的关键）

```
              ┌──────────────────────────┐
              │   WebSocketChannel       │  拆帧 / 组帧（与 TCP 共用）
              └────────────┬─────────────┘
                           │ IWebSocketBackend
          ┌────────────────┴─────────────────┐
          ▼                                  ▼
  DotNetWebSocketBackend            WebGLWebSocketBackend
  （ClientWebSocket，原生平台）       （jslib → 浏览器 WebSocket / wx.connectSocket）
```

| 后端 | 编译条件 | 说明 |
|---|---|---|
| `DotNetWebSocketBackend` | `!#if UNITY_WEBGL \|\| UNITY_EDITOR` | 真 socket，走线程池收发 |
| `WebGLWebSocketBackend` + `WebSocketBridge` | `UNITY_WEBGL && !UNITY_EDITOR` | C# ↔ JS 桥，**收到的数据先入队、Update 里主线程派发** |

JS 侧文件：`Assets/Plugins/WebGL/websocket.jslib`，导出 4 个函数：

| 函数 | 作用 |
|---|---|
| `CyWsCreate(url)` | 建连接，返回自增 id |
| `CyWsSend(id, ptr, len)` | 发二进制（从 `HEAPU8` 拷一份再 `send`） |
| `CyWsClose(id)` | 主动关闭 |
| `CyWsState(id)` | readyState，1 = OPEN |

**JS → Unity 用 `SendMessage("WebSocketBridge", "OnMessageBase64", "id,base64")`**，原因：
`SendMessage` 只能传字符串，二进制必须 base64；指针方案（`ptr,len`）虽然零拷贝，
但生命周期稍不注意就读到已释放内存，小游戏转换层上更难排查，所以这里选稳的方案。

**四个必须知道的实现细节**（都是踩过的坑）：

1. `SendMessage` 入口在不同运行时不统一 → jslib 里做了三重兜底：`Module.SendMessage` → 全局 `SendMessage` → `window.unityInstance.SendMessage`。
2. `WebSocketBridge` 的方法必须挂 `[Preserve]`：它们只被 JS 反射调用，IL2CPP + Strip 会当"没人用"裁掉（症状：JS 日志说发了，C# 毫无反应）。
3. 收包**不能在 `SendMessage` 回调里直接派发业务**，必须先入队、`Update` 里主线程消费，否则会在 Unity 内部回调栈里重入游戏逻辑。
4. `HEAPU8.slice(...)` 必须拷贝：直接 `send(视图)` 会发出脏数据。

## 五、两种模式怎么共用一套业务

```csharp
public static class GameEntry
{
    public static GameMode Mode { get; private set; }
    public static NetworkService Network { get; private set; }   // 离线时为 null
    public static DataService Data { get; private set; }         // 两种模式都有
}
```

**推荐写法**（把"模式判断"收敛到一处，别散落全项目）：

```csharp
// 只读本地数据：两种模式都能用（联网时是缓存）
var save = GameEntry.Data.Database.Table<PlayerSave>().Get(PlayerSave.FixedId);

// 需要服务端权威数据时：显式判断
if (GameEntry.Mode == GameMode.Online && GameEntry.Network != null)
{
    GameEntry.Network.Request(Cmd.EnterWorldReq, body, OnEnterWorldAck);
}
else
{
    UseLocalSave(save);
}
```

**数据冲突策略（给后续联机留的口子）**

| 模式 | 本地数据的角色 | 上线后怎么办 |
|---|---|---|
| Offline | 权威 | — |
| Online | 缓存 | 登录成功后用服务端数据覆盖本地关键表；断线期间允许读缓存续玩，重连后以服务端为准 |

`DataService.IsAuthoritative` 就是给这个判断用的（离线 = true）。

## 六、小游戏（WebGL）专属注意事项

| 事项 | 说明 |
|---|---|
| 资源模式 | 用 `resource.json` 的 `playMode = 3`（Web），或 Bootstrap 选 `Web`；资源全走 HTTP 不落磁盘 |
| 文件系统 | `persistentDataPath` 落在 IndexedDB（小游戏由转换层映射）。**写入是异步同步的**，关键节点主动 `Save()`，别指望"关页面自动保存" |
| 存储容量 | 小游戏本地存储有上限（各家不同，通常几十 MB 级）；存档只存数据，别把图片/音频塞进去 |
| 域名白名单 | `wss` 必须加到小程序的 socket 合法域名；CDN 也要加 request 合法域名 |
| 混合内容 | https 页面下 `ws://` 与 http 资源都会被拦；一律 `wss` / `https` |
| 首包体积 | 微信小游戏有严格体积限制，资源必须走 CDN + YooAsset（代码随包，不能热更） |
| 文本/字体 | 别依赖系统字体渲染中文（小游戏缺字库）；正式项目用 TMP + 字体子集 |

## 七、排障

| 现象 | 判据 | 处置 |
|---|---|---|
| 存档"写不进去"（重进回到旧值） | 实体用了属性而不是字段 | 改成 `public` 字段 + `[Serializable]` |
| 改了数据但没保存 | `Get` 返回引用，改完没 `MarkDirty()` | 就地改之后调 `table.MarkDirty()` |
| 存档目录里没有文件 | 存档目录不可写（降级为纯内存） | 看日志 `[Data] 存档目录不可写`；查 `Application.persistentDataPath` |
| 联网模式起不来 | `GameEntry.Network == null` | 确认 `launch.json` 的 `gameMode` 是 1，且 Bootstrap 没覆盖成 Offline |
| WebGL 连不上（编辑器正常） | `ws://` 被混合内容拦截 | 改 `webSocketSecure: true` 用 `wss://` |
| 小游戏连不上 wss | 域名白名单没配 | 微信后台加 socket 合法域名（含端口一致性） |
| JS 说发了 C# 没反应 | `[Preserve]` 被裁 / GameObject 名不对 | 确认 `WebSocketBridge` 方法都有 `[Preserve]`，名字与 jslib 一致 |
| 一启动就疯狂重连 | 连接前误触发"已断开" | 已在 `WebGLWebSocketBackend.Close` 用 `wasActive` 守住；若改动此处注意别退回去 |
| 收到的包解析错乱 | 文本帧混进二进制流 | 协议只支持二进制；`DotNetWebSocketBackend` 会丢弃文本帧并告警 |

## 八、这一层刻意没做的事

| 没做 | 原因 |
|---|---|
| 账号/登录体系 | 属于业务；联网模式下登录页只是个示例壳子 |
| 服务端 | 框架只定协议与通道，服务端用什么语言都行（长度头 + 二进制体是通用约定） |
| 加密/压缩 | 通道层不掺业务；要加就在 `ByteBuffer` 前后自己包一层 |
| 云存档/多端同步 | 需要服务端配合，不在框架范围 |
| 存档加密 | 单机存档加密的收益远低于成本（客户端密钥必然可被提取）；防作弊要靠服务端校验 |
